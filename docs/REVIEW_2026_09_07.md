# TableSync review and repair — September 7, 2026

## Current position

TableSync has a working local Dinner/Hotpot workflow, with further repairs made in this review. It is not yet a verified production release. Real GitHub sign-in, managed database recovery, HTTPS deployment, and the remote acceptance gate remain unverified. The local environment currently has no GitHub OAuth credentials, so normal host sign-in cannot be completed here; the isolated browser-test identity is only test evidence.

The review began with 22 modified tracked files and additional untracked work from an earlier audit. That work was preserved and reviewed. This document distinguishes repairs made in this review from future product scope; no commit, push, or deployment is claimed.

Priority definitions: **P1** = safety, data consistency, privacy, or release blocker; **P2** = broken or incomplete core user workflow; **P3** = polish or later product improvement. Priorities for open items reflect their effect, not an assertion that every future feature belongs in the current MVP.

## P1 — repaired

| Problem | Result | Main evidence |
| --- | --- | --- |
| Guest changes could race menu generation; votes and shopping changes could cross workflow transitions. | Related mutations use the same room transaction lock. Generation and finalization use the current room state inside that lock. | Database workflow and stale-snapshot regressions. |
| Milk/dairy aliases and qualified entries such as "sesame seeds" or "milk allergy" could bypass allergy filtering; a gluten-free dish tag could override a gluten-containing ingredient. | Allergen matching recognizes aliases and qualified allergen families, and ingredient conflicts take precedence. Absence labels such as gluten-free no longer falsely indicate presence. | Menu engine allergy regressions, including generated menus for a guest with a sesame-seeds allergy. |
| Shared menus omitted required instructions for adjustable spice. | Final public menus include generic preparation instructions without guest names or private warnings. | Public DTO privacy regression and rendered share page. |
| Shopping client components received full guest records, including fields unnecessary for shopping. | Client shopping data contains guest identifiers/names only; other guests' private notes and emails are excluded from guest room records. | DTO assertions, component checks, and browser coverage. |
| Hosting could silently use local database safeguards when deployment metadata was omitted. | Recognized hosting platforms require deployed environment configuration, secure connections, and attribution; they cannot fall back to local mode. | Vercel/Cloudflare configuration regressions. |

## P2 — repaired or completed

| Problem | Result |
| --- | --- |
| A low-budget no-solution room had no recovery path for changing the budget. | Hosts can edit title, description, event type, date, location, budget, guest count, and public sharing during collection/planning. Guest responses remain; stale generation reports clear. Voting rooms require reopening preferences; finalized rooms first require undoing finalization, then reopening preferences. |
| Clearing optional preferences retained old database values. | Empty email, guest budget, and notes clear saved values. |
| Changing a Veto retained its old reason; hosts could not see Veto explanations. | Like/Neutral clear the reason; private plan cards show current Veto explanations. |
| A guest could overwrite another guest's shopping assignment through a direct mutation. | Guests claim unassigned items and release only their own assignment; hosts retain reassignment controls. |
| Guest notes were collected but invisible to the host; guests lost the route back to their saved preferences. | Host-facing guest details display submitted constraints/notes; guest navigation and same-room invite recovery expose saved preferences. |
| The invitation looked copyable but had no working copy action and only displayed a relative path. | A full invitation URL can be copied, with a selectable-field fallback when clipboard access is unavailable. |
| Server time zones could shift entered event times. | The date input records the browser's offset for the selected day, and displays show the viewer's time zone. Invalid calendar dates and nonexistent daylight-saving wall times are rejected. Existing dates saved incorrectly cannot be inferred or repaired automatically; hosts can correct them during collection. |
| Candidate truncation could hide affordable or compatible meals; equally split proteins under-served uneven dietary groups. | The current catalog is searched completely; main/protein quantities account for which guests can eat each dish. |
| Shopping rounding lost or created cents and rounded shared quantities before merging. | Estimated item costs preserve the scaled dish total; quantities round after merging. Monetary forms reject fractional-cent values. |
| Expired host sessions could be reported as generic mutation failures. | Framework sign-in redirects propagate through mutation handling. |
| No-solution generation announced that menus were ready for voting. | The result explains that no safe menu fits and directs the host to recovery. |
| Concurrent requests could time out waiting for the supported one-connection local pool. | Database transaction admission and execution now have explicit bounded waits; connection attempts are bounded too. |
| Saving a vote or shopping form discarded unfinished changes elsewhere on the page and reset shopping filters. | Successful saves refresh server data and the client navigation cache while preserving unrelated drafts and filters. A submitted Like/Neutral still clears its own Veto reason. |

## P3 — repaired

- Repeated preferences from one guest cannot inflate recommendation scores; preferences from distinct guests still count.
- Dinner dishes that also have Hotpot roles retain the correct Dinner ordering.
- Guest detail disclosures have accessible control sizing, and notes wrap on narrow screens.
- The README and audit records distinguish current local verification from external release requirements.
- Failed-generation guidance clears when a guest actually changes preferences or a new guest joins, and the room returns to collection. Unchanged submissions and duplicate joins preserve the current report.

The first database run exposed two incorrect new test assumptions (guest budgets are informational; the top Hotpot plan need not require spice adjustment) and a transaction-admission timeout with five concurrent joins. The fixtures were made deterministic, admission was bounded appropriately, and the complete database gate subsequently passed.

The first browser attempt encountered terminated connections from the experimental local Prisma proxy before completing fresh-room workflows. That attempt was stopped and is not counted as acceptance. The existing local service was restarted without resetting data; browser batches were then rerun. Screenshot capture was also corrected to start at the top of the page, avoiding misleading sticky-header placement in full-page images.

The first WebKit Dinner run revealed a test synchronization race: the next form was filled after the Server Action response but before the previous save's full-page navigation finished. Mutation tests now wait for the new mutation URL and completed network activity before asserting saved state. The initial WebKit rerun passed with this correction; no product assertion was removed or relaxed. The independent follow-up below then identified a separate, real draft-loss defect in that full-page navigation behavior.

## Independent follow-up review

Two additional subagents independently reviewed the menu/shopping/date logic and state/authorization boundaries. The second pass found a P1 qualified-allergy matching regression and stale failure guidance; it found no additional confirmed permission or room-lock bypass. A separate client review found P2 draft loss when another form was saved.

The draft regression was reproduced against the previous production build: a Veto explanation entered before saving another plan's Like was replaced with an empty value. New browser assertions cover that exact sequence, preserving an unsaved Purchased checkbox while an assignment is saved, preserving the Purchased filter through another save, and clearing the submitted form's Veto reason after changing to Like. During verification, the new client navigation exposed duplicate preference-save feedback; the redundant banner was removed.

The follow-up added seven engine unit cases and one database regression for generation-report invalidation. The current totals above include these additions.

Verification also caught stalls after introducing synchronous server revalidation into workflow actions. The database changes and audit completed, but the page transition remained pending. That added revalidation was removed; successful saves refresh dynamic data and the navigation cache from the client after the action resolves. The precise framework transition cause was not established. Two tests tied only to that discarded invalidation implementation were removed; browser assertions check the actual saved values and preserved drafts.

A separate Hotpot retry completed the final shopping save and retained its filter, but an added test wait for the raw response stream never resolved. That redundant wait was removed; tests await the successful client URL refresh and assert the rendered saved state. The Hotpot rerun passed with all draft/filter assertions intact.

Final follow-up browser verification passed all 16 applicable scenarios across Chromium, Firefox, and WebKit, with the same five intentional skips listed above. WebKit initially exceeded a five-second room-creation assertion while the form was still submitting; creation now uses the same bounded 20-second allowance as other save checks, and the complete WebKit batch passed. These results verify behavior; they do not replace the outstanding remote performance gate.

Earlier reports are historical evidence and should not be treated as verification of this changed worktree.

Known execution limits: the local Prisma development proxy has previously become unstable under prolonged tests; it is not a substitute for managed PostgreSQL acceptance. Real OAuth callbacks, remote deployment/recovery, a production dependency audit, and a new Lighthouse run have not been claimed in this review.
